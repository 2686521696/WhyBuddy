## 二、下一轮第一件事

### 目标

精修时，**用户没提到的模型段不许被重写**。验收：`workflow` / `rbac` 在
「给某页加模拟数据」这类指令下指纹**未变**。

### 为什么不是 Merge Patch

已经试过，接不进去。`v5_capability_executor.py:492`：

```python
model = run_spec_first(goal, refine=_spec_refine, ...)["model"]
```

spec-first 天生「从 spec 树重新生成」，出口**永远是完整模型**。合并器看到六段
齐全就判「没按补丁交付」，原样放行。**补丁语义和这条链的架构不兼容**——这不是
接线问题，是方案选错了。

`services/merge_patch.py` 本身是对的（RFC 7386 逐行实现，12 条测试 + 2 个变异
全咬住），留着不删：将来若有真正按补丁产出的生成器，直接可用。

### 正确修法

**沿用同一个文件里已经存在的做法**。`v5_capability_executor.py:478-481`：

```python
if _reuse_style:     print("精修沿用上一版风格段")
if _reuse_language:  print("精修沿用上一版设计语言")
```

「精修沿用上一版」这个模式仓里已经有了，**只是只用在风格段上**。把它扩展到
模型段：精修时未被指令涉及的段**直接从基线复制，不进重新生成**。

思路同 Kubernetes server-side apply 的**字段归属**——谁拥有哪一段，重新生成就
不许覆盖不属于它的部分。是本仓已有的惯用法，不是新发明。

要动的地方：`run_spec_first` 的参数契约 + spec-first 内部的分支。**比之前任何
一次改动都深，别在上下文余量不足时动。**

难点：怎么判断「指令涉及哪几段」。可选方案（按稳妥度）：

1. 让精修的 SPEC 步顺带声明它需要改哪几段（多一个字段，不多一次调用）
2. 默认只允许改 `datamodel` / `page`，其余段一律沿用，用 env 开关控制
3. 关键词启发式（**不推荐**，本仓对未标定的启发式一贯保守）

### 开局三条命令

```bash
git log --oneline -12
slide-rule-python/.venv/bin/python -m pytest tests/test_refine_merge_reaches_the_live_path.py -v
cat slide-rule-python/tests/test_refine_merge_patch.py     # 为什么走到这一步
```

那个 strict xfail 会告诉你「合并还没落到真实链路」；修好之后它会 XPASS 报错，
逼着摘标记——不会出现「修好了但判据还挂着没人发现」。

## 三、验收方法（重要，别用错尺子）

**判据是逐段指纹 + 菜单保留数，不是「变没变」。**

早上用「四页字节变没变」验精修，4/4 变了就判通过——那只能证明「有反应」，
**全量重写同样让 4/4 都变**。逐段指纹才看得出是增量还是重写。

第二轮的指令必须针对**第一轮确实存在的页面**。踩过一次：指令写死「预警消息
中心」而第一轮没这一页，模型必须新增，指纹全变里有一部分是合理的，判不出问题。

菜单判据用**保留了几个名字**，不是 `n1 == n2`——加一页不算被换掉。
