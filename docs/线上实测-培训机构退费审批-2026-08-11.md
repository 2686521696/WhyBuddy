# 线上实测：培训机构退费申请与审批（2026-08-11）

跑一道**关系密集 + 双点驳回**的真实题目，全程抓 `[enrich-timing]`，目的是验收当天
上线的四项改动在真产出上到底起没起作用。

    题目：做一个校外培训机构的退费申请与审批系统：家长提交退费申请并选择要退的报名课程；
         教务核算已上课时与可退金额；财务复核后打款；核算或复核不通过要退回给上一环并
         写明原因；每笔退费都要能追溯到原始报名与缴费记录。
    链路：generate → gate → identity_theme → freeform_blocks → monitor_overviews（一步不减）
    线上版本：5bf5ec5（`index-CLmiPfpW.js` / `index-DOVYr0pJ.css`，与本地构建产物 md5 一致）

## 一、结论：这一趟逮到一个**我自己引入的真 bug**

当天 `6c1a9e1` 把"驳回不许铺成正向下一步"的派生逻辑收成一处共用。判据第一版是
**"优先无条件边，其余按目标声明序取最近的"**。这道题的产出当场把它打穿：

    [0] refund_draft  [1] academic_review  [2] academic_return ← 驳回
    [3] finance_review [4] finance_return  [5] payment_pending  [6] refund_paid [7] refund_closed

    academic_review → finance_review    「已上课时与可退金额核算通过」   ← 两条都有条件
    academic_review → academic_return   「报名或课时数据不完整…」        ←

两条都有条件 → 落到"取目标声明序最近的" → 选中下标 2 的 **academic_return**，
也就是一头拐进驳回分支；而它只有一条回环边（→ academic_review，已走过），主链路
在第 3 步就断了：

| | 应该是 | 改动后实际给出的 |
| --- | --- | --- |
| 主链路 | 申请 → 教务核算 → 财务复核 → 待打款 → 完成打款 → 归档（6 步） | 申请 → 教务核算 → **教务退回**（3 步） |
| 分支出口 | 教务退回、财务退回（2 个） | 财务复核、财务退回、待打款、完成打款、归档（5 个） |

**比不改还糟**：原来只是把驳回错插成一步，改完是把 4 个真正的正向节点整段踢出步骤条。

根因是"模型按流程顺序声明节点"这个假设太弱。作者习惯**把驳回节点紧挨着它的来源
写**（教务核算后面立刻写教务退回），所以驳回的下标恒定小于下一个真步骤，"取最近的"
必然选中驳回。

已改成结构判据：**比较两条边各自还能往前走多远，取更长的那条**。驳回节点通常只往
回连或直接终止（前向链长 1），真正的下一步后面还挂着整条流程（这里长 4）。长度相同
才退回旧判据（无条件优先 → 声明序靠前优先）。前向图按定义无环（下标严格递增），
链长记忆化递归即可。

这份 workflow 已经**原样**进了夹具（`workflow-steps-single-source.test.ts`），并配了
一条反向断言确认夹具真的复现那个形状（驳回下标 < 下一步下标、且两条出边都带条件），
免得哪天它"碰巧对了"。把判据换回旧版，两条测试如实变红。

## 三、refEntity 契约（当天 `4820e7c`）：模型 100% 采纳，但这道题一个都没救到

| 项 | 值 |
| --- | --- |
| `type:"ref"` 字段 | 13 |
| 声明了 `refEntity` | **13（100%）** |
| 声明悬空（门禁该拦） | 0 |
| 【反事实】老的名字猜测本来能认出 | **13（100%）** |
| 靠声明才救回来的 | **0** |

两件事要分开说：

* **契约那条规则生效了**——提示词里加的 `refEntity` 规则，模型一条不落地全带上了，
  而且 13 个目标全部指向真实存在的实体，门禁零 finding。
* **但这道题不需要它**。模型给字段起的名字都很规矩（`enrollment_id` → `enrollment`
  之类），老的词干猜测也能 100% 认出来。当初那个"1689 个 ref 只认出 41%"是在 181 份
  **存量**模型上量的，那批里有 `assigned_team → oncall_teams` 这种词干完全不同的命名。

所以这一趟只证明了"新键能被稳定产出"，没证明"它救回了多少"。要验后者得挑一道命名
会分叉的题（或者直接回放那 181 份存量模型）。

## 五、生图未配置带来的三处降级（本地环境，不是产品 bug）

日志自己说清了：

```

    生图未配置（IMAGE_API_URL / IMAGE_MODEL / IMAGE_API_KEY 需三项齐全）
```

影响面比第一版记的小，两处要更正（2026-08-11 复核）：

1. `monitor.sheet got=0 mediaGot=0` —— 参照板没出。**这条是真的**，而且它有三个
   下游一起没了：喂设计 LLM 排版的那张图、`sheet_palette → appIdentity.chartColors`
   （前端真会用，作为 `extractedCharts`）、应用中心卡片的画面。
2. ~~`primary=None` 说明 generatedTheme 一个色值都没有~~ —— **我记错了**。
   契约本来就只有 `{label, seed}` 两个字段，`seed` 就是那个色值（这趟是
   `#2F6F78`，合法）。`primary` 是**验证脚本 `fresh_topic_shot.py` 里的过期
   字段名**（旧版契约要 LLM 吐 11 个色值，早改成只吐 seed 了），跟生图没关系，
   也不是降级。
3. `palette: hue_ok=False`，off-palette 残留 `#008300` / `#eda100` —— 没有参照板
   可取色，`chartColors` 没写进去，前端回落到账本色序，而设计 LLM 自己挑的两个
   状态色不在色板里。这条跟生图有关，但**不经过 generatedTheme**。

降级是**如实**的：链路照常跑完，纯文字路径仍然设计出 52 节点的总览。

### 顺带查出来的：主题那一步在做白工

追 `primary=None` 时发现的，跟生图没配无关，配了也一样：

* Python 侧 `enrich_identity_theme` 每趟花 ~11s 调一次 LLM 选出 `{label, seed}`，
  写进 `appbundle.appIdentity.generatedTheme`
* 前端 `resolveIdentityTheme(_themeId, _generatedTheme, …)` **两个参数名都带下划线**，
  函数体直接 `return deriveIdentityPalette(BRAND_SEED, …)` —— 2026-08-03 的裁决是
  「全站一个颜色」，这个 seed 读进来就被丢掉

两边的注释还互相矛盾：前端写着"为选这一个色值要先生一张 ~74s 的图，**整段移除了**
（见 Python 侧 identity_theme_gen）"，而 Python 侧只把**生图**那半段关掉了
（`use_reference_image` 默认 False），选色的 LLM 调用还留着。Python 的 docstring
也过期，仍写着"generatedTheme 缺失时前端落回 appIdentity.theme 那个 8 选 1"——
前端现在也不落回 8 选 1，永远是 BRAND_SEED。

所以是每趟约 11 秒的纯白工（352s 里的 3%），不大，但两边说法不一致这件事本身
会误导下一个人。**本轮没动**，因为要么删 Python 那一步、要么让前端重新采纳，
这是产品裁决不是实现问题。

**但有一处值得补**：`/api/health` 报了 `llm.keyPresent` 和 `blockNarrowing.effective`，
**没有报生图三项在不在**。而这恰恰是"缺了不报错、只是产物变难看"的那类配置——线上到底
配没配，从外面看不出来。建议把它加进健康端点（本轮没动，先记下来）。
