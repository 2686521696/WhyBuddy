## 最要紧的一条：我们的区块粒度切错了

`x-render` 的 `table-render` 是**一个包**，内部拆成三块：

```
packages/table-render/src/core/
  SearchView/     查询表单
  ToolbarView/    工具栏（刷新 / 列设置 / 全屏 / 密度）
  TableView/      表格本体（含 field.tsx / widgets.tsx 字段渲染）
```

也就是说：**一个「列表页」是一个区块**，搜索、工具栏、表格是它的内部结构。

我们做的正相反 —— 把同一件事拆成了四个平级区块：

```
FilterBar + StatusTabs + DataTable + BatchActionBar
```

后果很实在：

- AI 要装配四次，Gate 要查四次，每一次都可能出错（实测已经踩到两次：
  BatchActionBar 的 actions 空着、PageHeader 落进 footerBar）
- 四个区块之间要靠共享状态串（filterState / selection），每接一个都要改
  ExperienceBlockRendererProps
- 我一个一个手写，**这就是"费时间"的来源**

`ToolbarActionConfig` 的写法值得抄：

```ts
export type ToolbarActionConfig = {
  enabled?: Array<'refresh' | 'columnsSetting' | 'fullScreen' | 'density'>,
  columnsSettingValue?: ColumnsSettingValueType
  onColumnsSettingChange?: (val) => void;
}
```

**工具栏的每个功能是一个开关，不是一个区块。** 我正准备把 ColumnSetting 做成第
五个区块，照这个看是错的 —— 它应该是列表区块的一个 `enabled` 选项。

## 字段语义：应该是声明的，不是猜的

`x-render` 的列契约（`packages/table-render/src/types.ts`）：

```ts
valueType?: 'text' | 'money' | 'date' | 'dateTime' | 'code' | 'tag' | 'tags'
          | 'progress' | 'dateRange' | 'dateTimeRange' | 'image';
enum?: Record<string, string>;   // 当前列值的枚举
```

`jeecgboot` 的在线表单列配置（`OnLine/types/onlineConfig.ts`）同样是声明式：

```ts
fieldType?: string;      // 字段类型
dbType?: string;         // int / string
customRender?: string;   // 字典编码字符串，后转函数
linkField?: string;      // 他表字段
isTotal?: boolean;       // 参与合计
groupTitle?: string;     // 分组表头
children?: OnlineColumn[];  // 多级表头
```

我们的 `fieldSemantic()` 是**从数据猜**的（看值像不像日期、有没有枚举选项）。
猜就会猜错 —— 之前那个 enum 列打印 `frozen` 而不是「已冻结」的 bug 就是这么来的。

`refine` 的推断器有 **13 种**（`packages/inferencer/src/field-inferencers/`）：

```
array boolean date email image nullish number object relation richtext text url
```

我们只有 7 种：`money number date datetime enum text id`。**缺 email / url /
image / richtext / relation / boolean / array 七种**——邮箱不出 mailto、链接不
可点、图片列印一串 URL，都是这个缺口。

## formily：两条我们没有的协议能力

`packages/json-schema/src/types.ts`：

```ts
['x-decorator']?: Decorator       // 外壳（FormItem / Card）
['x-component']?: Component       // 控件（Input / Select）
['x-reactions']?: SchemaReactions // 声明式联动
['x-pattern']?: Pattern           // editable / disabled / readOnly / readPretty
```

1. **`x-decorator` 与 `x-component` 分离** —— 这正是我们摸索出来的 `BlockShell`
   与区块本体的关系（"不要 card 包裹"那一轮）。区别是他们把它做成了**协议字段**，
   我们是硬编码在渲染器里（`surface: card | plain`）。
2. **`x-reactions` 声明式联动** —— 我们完全没有。区块之间目前只能靠共享
   `filterState` 这一个特例互相影响，"选了省份之后城市下拉只显示该省的市"这类
   需求现在写不出来。
3. **`x-pattern` 四态** —— 同一份 schema 可以是可编辑 / 禁用 / 只读 / 阅读态。
   我们没有"只读"这个概念，详情页和表单页是两个不同的区块。

## 结论与建议

### 该改的（按价值排）

1. **把列表页收成一个复合区块**（照 `table-render`）。
   搜索 / 状态页签 / 工具栏 / 表格 / 批量操作 / 分页 是它的**内部开关**，不是六个
   平级区块。这一条直接解决"费时间"：AI 装配一次而不是四次，Gate 查一次而不是四次，
   区块间不用再串状态。
   代价：已经建好的 FilterBar / StatusTabs / BatchActionBar 要降级成列表区块的
   `enabled` 选项，或者保留给"不带表格的页面"用。

2. **字段语义从推断改成声明，并从 7 种补到 13 种**（照 refine + x-render）。
   声明来自数据模型的字段定义，推断只作为兜底。

3. **补 `x-pattern` 只读态**（照 formily）。有了它，详情区块就是表单区块的
   `readPretty` 形态，不用两套渲染器。

### 该考虑但不急的

4. `x-reactions` 声明式联动 —— 能力很强，但它要求区块之间有个求值器，是个大件。
5. jeecg 的合计行 / 他表字段 / 多级表头 —— 真实业务里高频，但属于表格区块的内部
   能力，等第 1 条做完再补更省事。

### 已经做对的

- 区块携带 `capability` + `allowedRegions` 双向约束（对应 lowcode-engine 的
  nestingRule、Puck 的 SlotField.allow）
- 区域带 `evidence`（出自哪个真实页面）
- Gate 用规则判而不是让模型凭感觉判

# 结论变了：**我上一轮的建议是错的**

上一轮只看了五个，我建议「照 x-render 把列表页收成一个复合区块」。看完 20 个之后
这个判断站不住：

**x-render 是组件库，不是装配平台。** 它的 `table-render` 是给人手写配置用的一个
大组件。我们的场景是 AI 装配——把六样东西塞进一个区块，等于把六份 propsSchema 合成
一份巨型 schema，模型更难填对，Gate 也退化成一次大检查。

**NocoBase 才是同一个问题形状**（AI/无代码平台，antd + formily，23.6k），而它的
答案是第三种，我之前根本没想到：

## NocoBase 的做法：分族 + 显式连接

```
packages/core/client/src/modules/blocks/
  data-blocks/    绑数据源的：table / form / details-multi / details-single
                  / list / grid-card / table-selector
  filter-blocks/  **不展示数据，只筛别的区块**：form / collapse
  other-blocks/   纯内容：markdown / divider
```

筛选区块不是并进数据区块，也不是靠隐式共享状态——它**显式声明自己筛谁**：

```ts
// SchemaSettingsConnectDataBlocks.tsx
let { targets = [], uid } = findFilterTargets(fieldSchema);
targets.push({ uid: block.uid });          // 勾上就是"我筛这个区块"
dn.emit('patch', { schema: { 'x-filter-targets': targets } });

// 只能连同一个 collection 的数据区块；跨表要额外指定关联字段
if (isSameCollection(block.collection, collection)) { ... }
else { /* 选 target.field 作为关联字段 */ }
```

## 这一条暴露了我们一个真 bug

`ComponentsLibraryPage.tsx` 的 `visibleRows`：

```ts
for (const [entityId, list] of Object.entries(rows)) {   // ← 所有实体
  out[entityId] = list.filter(r => {
    for (const [field, want] of Object.entries(filterState.enumFilters)) {
      if (String(r.values?.[field] ?? "") !== want) return false;
    }
  });
}
```

筛选对**页面上所有实体**生效，只按字段名匹配。一页放两张表（订单 + 客户），只要
都有 `status` 字段，筛一个就把两个都筛了。StatusTabs 写 `enumFilters[field]` 时
同样不知道自己该筛哪张表。

NocoBase 的设计从构造上就不可能出这个问题。

# 修订后的方案

好消息：我们现在的结构**就是 NocoBase 的结构，只是少了显式连接那一环**。所以是
补一环，不是推翻重来。上一轮建的 FilterBar / StatusTabs / BatchActionBar 全部保留。

按价值排：

1. **区块分族** —— 目录里给每个区块加 `family`：
   `data`（自己取数展示）/ `filter`（筛别的区块）/ `action`（对别的区块做事）/
   `content`（纯内容）。这一族信息 AI 装配时比 `capability` 更有用：它直接告诉
   模型"这个东西是独立的还是要挂在别人身上"。

2. **filter / action 族必须声明 `targets`** —— 指向同页数据区块的 id。
   Gate 查三件事：target 存在、target 是 data 族、两者绑同一实体（或声明了关联
   字段）。这条直接修掉上面那个 bug，也让 BatchActionBar 知道自己操作的是哪张表。

3. **字段语义从推断改成声明，7 种补到 13 种**（refine 的 field-inferencers +
   x-render 的 valueType）。声明来自数据模型，推断只作兜底。

4. **补只读态**（formily 的 `x-pattern`）——详情区块 = 表单区块的 readPretty 形态。

第 1、2 条是这次调研的真正产出：它们同时解决了"AI 装配要装几次"和"筛选串台"，
而且不需要推翻已有的区块。
