# 区块建设执行顺序

2026-08-08 定。目标：**区块从 18 个长到能覆盖真实业务，且不靠手搓。**

路线的核心判断（来自 20 个开源项目的调研，见 `区块最佳实践-开源调研.md`）：

> 我们的契约层是插座，开源仓库是零件。别人生产验证过的东西，我们做适配入库，
> 不是发明。真正值钱的不是他们那几行 JSX，是**他们踩过的边界情况**。

## 阶段 0 · 合规底线（先钉死，贯穿全程）

搬之前必须先分清哪些能抄代码。**逐个查过许可证**：

| 可以抄代码 | 许可 |
|---|---|
| ant-design-pro / pro-blocks、pro-components、refine、formily、designable、jeecgboot-vue3、puck、craft.js、plasmic、brick-design | MIT |
| amis | Apache-2.0（保留版权声明） |

| ⚠️ 只能读设计，**不可复制任何代码** | 问题 |
|---|---|
| **NocoBase** | 源文件头部写明 AGPL-3.0 + 商业双授权。AGPL 传染，抄进来整个 WhyBuddy 都得开源 |
| **h5-Dooring** | GPL-3.0，同样传染 |
| **x-render** | 仓库与 package.json 都没有 license 字段 = 保留所有权利 |

**纪律**：
1. 这三个仓库的代码一行都不进我们仓库。它们的**架构思路**（NocoBase 的分族 +

2. 每搬一个区块，在目录条目里记 `source: { repo, path, license }`。这是合规
   要求，也是以后回查"这个边界情况是从哪学来的"的线索。

## 阶段 ① · 契约层封口

**为什么先做**：搬进来的区块得有地方插。契约没定死就开搬，等于边搬边改插座。

三件事，互相独立，可并行：

### ①a 区块分族 `family`

给 18 个区块各贴一个：

```
data     自己取数展示，能独立存在        DataTable / RecordDetail / MetricGrid / TrendChart …
filter   不展示数据，只筛别的区块        FilterBar / StatusTabs
action   不展示数据，对别的区块做事      BatchActionBar / QuickActionPanel
content  纯内容，不绑数据                ContentCard / PageHeader / FreeformInsight
```

思路来源 NocoBase 的 `data-blocks / filter-blocks / other-blocks`（只借结构，
不抄代码）。

**为什么比 `capability` 有用**：capability 说"我干什么"，family 说"我能不能单独
存在"。模型现在只知道 FilterBar 是 `filter`，不知道它离开表格就没有意义。

**验收**：目录里 18 个区块全有 family；给模型的清单里带上它。

### ①b `targets`：区块之间的显式连线

`filter` / `action` 族必须声明自己作用于哪个区块：

```json
"binding": { "targets": ["block-id-of-the-table"] }
```

**这一条修掉一个真 bug**（已复现）：`ComponentsLibraryPage` 的 `visibleRows`
对页面上**所有实体**套同一份 `enumFilters`，只按字段名匹配。一页两张表只要都有
`status` 字段，筛一个就把两个都筛了。

Gate 补三条：
- `target-missing` —— targets 指向的区块不在这一页
- `target-not-data` —— target 不是 data 族（筛一个筛选条没有意义）
- `target-entity-mismatch` —— 两者绑的实体不同（跨表要另外声明关联字段）

再补一条区域顺序规则（这是两根轴唯一真的有关系的地方）：
- `filter-after-target` —— filter 族所在区域必须排在 target 所在区域**之前**，
  否则是"先读内容再筛选"

**同时改**：`filterState` / `selection` 从页面级一坨改成按 target 分开存。

**验收**：造一页两张表（订单 + 客户，都有 status），筛一个另一个不动。

### ①c 字段语义：从推断改成声明，7 种补到 13 种

现在 `fieldSemantic()` 从数据猜（看值像不像日期、有没有枚举选项）。猜就会猜错
——之前 enum 列打印 `frozen` 而不是「已冻结」就是这么来的。

改成：**声明优先，推断兜底**。声明来自数据模型的字段定义。

种类照 `refine` 的 field-inferencers（13 种）+ `x-render` 的 `valueType`：

```
现有 7 种： money number date datetime enum text id
补 6 种：   email url image richtext boolean array/relation
```

**为什么必须在②之前**：搬进来的每个区块只要显示字段就会用到它。先搬 60 个再补
语义，等于回头改 60 个。

**验收**：邮箱出 mailto、链接可点、图片出缩略图，各一条用例。

### ①d 只读态（可以往后挪）

照 formily 的 `x-pattern`：`editable / disabled / readOnly / readPretty`。有了它，
**详情区块 = 表单区块的 readPretty 形态**，不用两套渲染器。

**为什么排在 ①c 后面**：它更侵入（要改现有渲染器），而且收益是"搬的时候少搬一
半"。如果 ①a-c 做完想尽快开搬，这一条可以挪到②进行到一半、真的发现在重复搬
"详情版/编辑版"时再做。

## 阶段 ② · 搬第一类：同栈 60~80 个

**不需要任何新基础设施，今天就能开工。**

### 搬运配方（每个区块固定六步）

1. **读实现**，重点不是 JSX，是**边界情况**：空态 / 加载态 / 错误态 / 权限 /
   分页边界 / 选中语义 / 联动
2. **写契约**：`family` + `capability` + `allowedRegions` + `regionsRationale`
   + `propsSchema` + `bindingSchema`（含 targets）+ `events`
3. **落渲染器**：用我们的基础组件重写，不复制源码结构
4. **记来源**：`source: { repo, path, license }`
5. **补用例**：至少钉住读到的那几条边界情况（这是搬运的真正产出）
6. **真跑一次**：装进页面看它在浏览器里对不对

### 搬运优先级（按"补我们最缺的"排）

| 批次 | 搬什么 | 来源 | 补什么缺口 |
|---|---|---|---|
| 1 | 列设置、可编辑子表、工具栏 | pro-components | 表格能力 |
| 2 | 指标卡带环比与迷你图、带页签的图表卡、饼图占比、排行 | pro-blocks DashboardAnalysis | 仪表盘 |
| 3 | 标签式筛选（可展开）、搜索框 | pro-blocks ListSearch* | 筛选区 |
| 4 | 高级详情、流程进度、关联单据 | pro-blocks ProfileAdvanced | 详情页 |
| 5 | 分步表单、高级表单分组、底部校验汇总 | pro-blocks Form* | 表单页 |
| 6 | 卡片列表、头像组、内容列表项 | pro-blocks List* | 列表变体 |
| 7 | 合计行、他表字段、多级表头 | jeecgboot-vue3 | 中式报表 |

**里程碑**：搬完批次 1-3，区块约到 35~40，112 个未接入的基础组件会释放一大批。

### 什么时候停

搬到第 20~30 个的时候做一次复盘：**哪些逻辑在反复重写？** 那就是该抽成 schema
的部分。这个观察是阶段③的设计依据——不是我拍脑袋定的。

## 阶段 ③ · 组件注册表 + 通用渲染器

**触发条件**：②进行到复盘点，且确实看到重复。不要提前做。

现在 139 个基础组件是**只能看的示例**：

```ts
export interface BaseComponentDef {
  name: string;                     // "Table"
  render: () => React.ReactNode;    // ← 零参数演示函数，真组件没暴露
}
```

要做的：

1. **注册表**：`component: Table` 能被名字引用、能接 props
2. **组合 schema**：区块 = `{ component, props, children[], bind{} }` 的树
3. **通用渲染器**：走这棵树——查组件、绑数据、接事件。
   最近的一条路是改造 `FreeformInsight`：它已经能渲染一棵树，只是渲染的是原生
   DOM 标签，不是基础组件
4. **嵌套合法性**：Form.Item 只能在 Form 下这类规则（lowcode-engine 的
   `nestingRule` 思路）

## 阶段 ④ · 灌第二类：amis 的 290+

amis 的例子是**纯 JSON 树**，形状跟我们区块 schema 一样：

```json
{ "type": "crud", "toolbar": [{ "type": "button", "actionType": "dialog",
  "dialog": { "body": { "type": "form", "body": [...] }}}] }
```

供给：**135 个页面例子 + 157 篇组件文档**（每篇里还有多个 schema）。

但它用的是 amis 自己的词汇（`input-text` / `crud` / `dialog`），不是 antd。所以
要一张**类型名映射表**：`amis type → 我们的基础组件 + 默认 props`。

有了③的渲染器 + 这张表，这 290+ 就能批量灌进来。

## 依赖与风险

```
①a family ─┐
①b targets ─┼──► ② 搬 60~80 ──► ③ 注册表+渲染器 ──► ④ 灌 amis 290+
①c 字段语义 ┘         │
①d 只读态 ············┘（可挪到②中途）
```

| 阶段 | 风险 | 可逆性 |
|---|---|---|
| ① | 低。纯契约扩展，改的是目录 + Gate | 高 |
| ② | 低。一个一个加，每个独立 | 高，单个可回滚 |
| ③ | **中高**。动渲染核心 | 中，需要分支保护 |
| ④ | 中。映射表可能有大量长尾对不上 | 高，一条一条灌 |

**最容易出错的地方**：③提前做。没有②积累的重复观察，schema 会设计成我想象的
样子而不是真实需要的样子。这个项目已经有过一次教训——第一版区域名是我编的，
后来照 pro-blocks 的 29 个真实页面全部重来。
